真正找模型短板，不能只看总 mAP，也不能只看特征图。正确路线是：

> 先确定“哪些目标没检测出来” → 再定位“信息在哪个阶段丢失” → 最后针对这个阶段设计改进。

创新点应当是“有证据的机制改进”，不是简单换一个注意力或上采样模块。

## 1. 先把错误拆开

重点统计：

* 漏检 FN：模型完全没有候选框。
* 定位不准：有候选框，但 IoU 只有 0.1～0.5。
* 低置信度：位置正确，但 confidence 很低。
* 密集目标互相抑制：NMS 前有，NMS 后消失。
* 背景误检：枝叶、高光、果梗被识别成花。
* 标注歧义：同一花簇到底算一个还是多个。

验证时把置信度降到 `0.001`，分别计算：

* Recall@IoU=0.3
* Recall@IoU=0.5
* Recall@IoU=0.75
* NMS 前召回率
* NMS 后召回率（现在有一些端对端的没有这个nms了）
* 每张图误检数量
* 匹配成功目标的平均置信度

判断方式：

| 实验现象                        | 主要短板              |
| --------------------------- | ----------------- |
| IoU 0.3 召回高，IoU 0.5/0.75 很低 | 回归、边界定义或定位损失      |
| 所有 IoU 下召回都低                | 特征消失、正样本分配或数据问题   |
| NMS 前召回高，NMS 后明显下降          | 密集目标抑制问题          |
| 位置正确但置信度普遍低                 | 特征区分度或置信度学习问题     |
| 训练集很好、验证集明显差                | 过拟合、数据量或场景分布问题    |
| 训练集和验证集都差                   | 模型能力、标签一致性或任务定义问题 |

## 2. 必须按目标大小统计

不要只用整体 mAP。应根据“送入 832×832 模型后的真实像素尺寸”分组，例如：

* 最短边 `<8 px`
* `8～16 px`
* `16～32 px`
* `32～64 px`
* `>64 px`

同时再按目标面积的 Q1、Q2、Q3、Q4 四分位统计召回率，避免固定阈值不适合花簇数据。

如果结果是：

```text
最小 25% 目标 Recall = 0.28
其余目标 Recall = 0.75
```

这才能证明“小目标特征提取”确实是核心短板。否则即使增加 P2 有提升，也可能只是参数量增加带来的，并不能支撑论文创新。

## 4. 特征图要这样看才有意义

只看“特征图亮不亮”不能证明模型短板。至少要回答：

1. P2 中目标是否清晰？
2. 进入 P3 后目标响应是否消失？
3. 目标响应是否被枝叶背景淹没？
4. P3/P4/P5 中哪个层负责了这些目标？
5. 小目标区域与邻近背景的特征差异是否越来越小？

可以计算 GT 框内部与周围背景的特征距离，而不只是输出热力图：

```text
特征区分度 = 目标区域平均特征与邻近背景平均特征的距离
```

如果 P2 区分度较高、P3 急剧下降，就能够定量证明早期下采样造成信息损失。


## 6. 一项创新是否站得住，要形成完整证据链

例如：

```text
现象：
最小四分位目标召回率只有 31%

定位：
裁剪放大后提升到 70%
P2 特征明显，P3 特征消失
NMS 前后召回差距很小

结论：
短板在早期下采样导致的小目标细节丢失

方法：
语义门控的轻量 P2→P3 细节注入

验证：
小目标召回提高
中大目标性能不下降
参数量、GFLOPs、显存和延迟明显低于完整 P2
```

这就是一条可以写进论文的创新逻辑。

无论分类、检测、分割还是跟踪，都可以用同一套思路：

> 错误分组 → 属性切片 → Oracle 对照 → 定位阶段 → 设计针对性改进。

不要先问“哪个模块还能换”，而是问：

> 性能主要损失在输入信息、特征表示、任务头、训练策略，还是后处理？

## 一套通用诊断框架

任何视觉模型都可以抽象成：

```text
图像 → 数据预处理 → Backbone特征 → 特征融合/任务头 → 原始输出 → 后处理
```

依次做替换或消融：

| 诊断实验                  | 想确认的问题              |
| --------------------- | ------------------- |
| 提高分辨率、裁剪目标            | 输入信息是否不足            |
| 清洗标签后重新验证             | 标注是否限制上限            |
| 比较浅层和深层特征             | 信息在哪一层丢失            |
| 固定 Backbone，换简单/复杂任务头 | Backbone 还是 Head 不够 |
| 关闭后处理、查看原始输出          | 后处理是否制造错误           |
| 小数据集过拟合测试             | 代码、损失和优化是否正常        |
| 按场景和属性统计              | 模型具体在哪些条件下失败        |

其中最重要的是 Oracle 实验：人为提供一个更理想的中间结果，看性能能提升多少。哪个 Oracle 提升最大，短板大概率就在哪。
